# Design — Product docs single source of truth (hub docs repo + Outline sync)

**Date:** 2026-07-18
**Status:** Approved, awaiting implementation plan
**Scope:** ws-project-hub v0.2.0 + docs-agent v3.1.0 (both additive)

## Problem

WS products span multiple sub-repos (app, admin, frontend, …) under a `<project>-main` hub
(ws-project-hub convention). Documentation today has no product-level home:

- Cross-repo dev docs (architecture, decision log, client-provided materials) have no single
  place that every sub-repo session can read **and write**.
- User-facing docs must serve helpdesk and other non-dev readers through Outline
  (docs.wsagency.io), but nothing connects the git docs to Outline.
- AI-generated "repo explained" onboarding pages were starting to live in a separate repo,
  drifting from the docs they duplicate.

Goal: one source of truth in git, writable from any sub-repo session, published to Outline
for non-dev readers, with Outline edits flowing back through review.

> **Amendments (2026-07-21, at implementation):** (1) command names map through the
> consolidation rename table (`/hub-*` → `ws-hub-*`; versions ws-project-hub 0.3.0,
> docs-agent 3.2.0); (2) sync state lives in **`.outline-sync.json`**, not `.yaml` —
> the script is stdlib-only and Python's stdlib has no YAML parser; (3) `--normalize`
> and image/attachment upload are deferred to a later version (recorded in the
> script's docstring and the changelog).

## Decisions

| Question | Decision |
|---|---|
| Where does product-level doc SoT live? | Dedicated `<project>-docs` sub-repo, registered in `project.yaml` with `role: docs` |
| Per-repo vs central split | Hybrid by scope: ALL user docs are product-level (docs repo); dev docs split — cross-repo/product in docs repo, repo-specific stays next to the code |
| Outline sync direction | Push (git → Outline) + pull-back (Outline → branch → PR). Git stays authoritative through review |
| Sync mechanism | Deterministic Python script (`outline-sync.py`, stdlib only) using the Outline REST API; `/ws-docs` verbs orchestrate it |
| Plugin split | ws-project-hub owns hub topology (`role: docs`, scaffolding); docs-agent owns docs lifecycle (routing, publish/pull-back/explain) |
| "Repo explained" page | Generated Outline-safe **markdown** (`docs/explained.md`), not HTML; becomes the Outline collection landing doc; separate explained repos are retired |

## Convention: product docs repo

At most one repo per hub carries `role: docs`. It is a normal sub-repo (own git, mounted by
`invoke-ai.sh`, cloned by `/hub-clone-all`) with this layout:

```
<project>-docs/
├── README.md
├── CLAUDE.md                    ← writing rules (scope, Outline-safe profile)
├── docs/                        ← USER track (Diátaxis) → syncs to Outline
│   ├── index.md
│   ├── explained.md             ← GENERATED by /ws-docs explain
│   ├── tutorials/  how-to/  reference/  explanation/
│   ├── assets/                  ← images (uploaded as Outline attachments)
│   └── release-notes/
├── dev-docs/                    ← PRODUCT-level internal (never synced)
│   ├── architecture.md          ← cross-repo, written by hub-architect
│   ├── decisions/               ← product ADRs
│   ├── client-materials/        ← material received from the client
│   └── runbooks/
└── .outline-sync.yaml           ← sync state/mapping (committed)
```

Split rule: **does it concern more than one repo, or the client, or any end user → docs repo.**
Sub-repos keep only repo-specific `dev-docs/` (internal modules, own ADRs, runbooks) and no
user track. `CHANGELOG.md` stays per-repo (product-level changelog aggregation is out of scope).

Writing path from any sub-repo: nested layout means the docs repo is always present at
`<hub>/<project>-docs/` and mounted in every `invoke-ai.sh` session, so any session can edit
it directly — no submodules or copying. The hub `CLAUDE.md` points sessions and people at it.

## ws-project-hub changes (v0.2.0)

1. `project.yaml` schema: optional `role: docs` on a repo entry; validation: at most one.
2. `/hub-init`: after repo registration, offers "Create a product docs repo?" — scaffolds
   `<project>-docs` (git init + layout above) and registers it with `role: docs`.
3. `/hub-add-repo`: can mark an added repo with `role: docs`.
4. Generated hub `CLAUDE.md`: new section pointing at the docs repo as the product doc SoT.
5. `hub-architect` agent: when a docs repo exists, writes cross-repo outputs to
   `<project>-docs/dev-docs/` instead of the hub's `docs/`.
6. `project-hub-conventions` skill: documents the `role` field and the docs repo convention.

No changes to `invoke-ai.sh`, `/hub-sync`, `/hub-status`, `/hub-clone-all` — the docs repo is
an ordinary sub-repo to them.

## docs-agent changes (v3.1.0)

**Hub detection:** `/ws-docs` walks up from cwd looking for a `project.yaml` whose `repos[]`
contains `role: docs`. Found → "hub mode", with the docs repo path resolved from it.

Routing in hub mode:

| Verb | Behavior |
|---|---|
| `write` (user audience) | Always to docs repo `docs/` — user docs are product-level by definition |
| `write` (dev audience) | Scope prompt: **this repo** (local `dev-docs/`) or **product** (docs repo `dev-docs/`) |
| `adr` | Scope prompt: repo ADR (local `dev-docs/decisions/`) or product ADR (docs repo `dev-docs/decisions/`) |
| `architecture` | Product scope → docs repo `dev-docs/architecture.md` (delegates to hub-architect); repo scope unchanged |
| `changelog`, `release-notes` | Repo-level, unchanged |
| `explain` (new) | (Re)generate `docs/explained.md` in the docs repo |
| `publish` (new) | Lint the Outline-safe profile, then `outline-sync.py push`; flags `--dry-run`, `--normalize` |
| `pull-back` (new) | `outline-sync.py pull`, then Claude creates branch + commit + PR (tea) |

The scope answer can be cached in `.claude/docs-config.yaml` as `default_scope: repo | product | ask`.
`publish`/`pull-back` work in **any** repo containing `docs/` + `.outline-sync.yaml` — not only
hubs (the marketplace repo itself can publish its user docs).

## Outline-safe markdown profile

Outline stores documents as ProseMirror JSON; markdown is a potentially lossy import/export
format. The `docs/` track is therefore restricted to a profile that round-trips cleanly.
`dev-docs/` is not synced and not restricted.

**Allowed:** headings, bold/italic/strikethrough, blockquotes, ordered/unordered/task lists,
inline code, fenced code blocks with language, ` ```mermaid ` diagrams, `:::info` /
`:::warning` / `:::tip` notices, tables, `$$LaTeX$$` math, images, links, and rich embeds
(a supported provider URL — YouTube, Figma, Loom, Miro… — alone on its own line).

**Banned (lossy or unsupported):** raw HTML (Outline has no HTML support at all), footnotes,
definition lists, emoji shortcodes, `==highlight==`, sub/superscript, manual heading IDs.

`publish` lints the profile before pushing and refuses with a per-file violation list.

Two things the sync script must actively translate:

1. **Internal links:** relative `.md` paths in git ↔ `/doc/<urlId>` in Outline, both
   directions, via the mapping in `.outline-sync.yaml`.
2. **Images:** relative paths under `docs/assets/` are uploaded via the attachments API on
   push (URL rewritten); on pull-back, new Outline attachments are downloaded into
   `docs/assets/` and rewritten to relative paths.

Lossiness mitigation: after the first publish, `--normalize` pulls Outline's own
serialization back into git so future pull-back diffs contain no formatting noise.

## The explained page

`/ws-docs explain` generates `docs/explained.md` — a single rich onboarding page built from
SoT inputs (`project.yaml`, sub-repo READMEs, `dev-docs/architecture.md`, existing `docs/`):
what the product is, a mermaid architecture diagram of repos and their relationships, workflow
diagrams, a roles table, install/quickstart, and links to deeper docs.

- Header comment: `<!-- GENERATED by /ws-docs explain — do not edit by hand -->`
- Regenerated on demand; never hand-edited; markdown SoT remains the only source.
- On publish it becomes the **first top-level document in the Outline collection** (Outline
  has no formal "landing page" concept — first position is the convention), so helpdesk and
  new team members open it first, with rendered diagrams.
- An interactive HTML variant (`--html`) is a possible later addition, out of scope for v1.

## outline-sync.py contract

Location: `plugins/docs-agent/scripts/outline-sync.py`. Python 3, stdlib only (urllib, json,
hashlib) — nothing to install. Python 3 returns to the README prerequisites (it left with
ws-claude-sync's removal).

**Auth:** `OUTLINE_API_TOKEN` env var, fallback `~/.config/ws-docs/outline-token`. Never in
the repo. Instance URL defaults to `https://docs.wsagency.io`, overridable in
`.outline-sync.yaml`.

**State** (`.outline-sync.yaml`, committed):

```yaml
outline:
  url: https://docs.wsagency.io
  collection_id: <uuid>            # created on first push if missing
docs_dir: docs
documents:                          # managed by the script
  docs/tutorials/getting-started.md:
    id: <outline-doc-uuid>
    last_synced_hash: <sha256 of last pushed markdown>
    last_synced_revision: <outline revision at last sync>
```

**Push algorithm:**
1. Walk `docs_dir` for `.md` files; folder hierarchy maps to nested documents
   (`index.md` = parent document of its folder; `explained.md` = first top-level document).
2. Per file: skip if content hash equals `last_synced_hash`. Otherwise compare Outline's
   current revision with `last_synced_revision`; if Outline changed too → **conflict: skip
   and report** (override with `--force`; normal resolution is a pull-back PR).
3. Create/update via API with links and images rewritten. Files deleted from git →
   **archive** the Outline document (never hard-delete).
4. Update state only for successful operations; re-runs are idempotent.

**Pull algorithm:**
1. For each mapped document, fetch content; if revision differs from
   `last_synced_revision`, write markdown into the working tree (reverse link rewrite,
   download new attachments).
2. Documents created in Outline that have no mapping → new files mirroring the Outline
   hierarchy.
3. The script only writes files and prints a report. The `/ws-docs pull-back` command does
   git work: branch `docs/outline-pull-back-<date>`, commit, PR via tea. After the PR merges,
   the next publish converges state.

Both `push` and `pull` support `--dry-run` and emit a machine-readable summary (usable from
CI without Claude).

## Error handling

- Missing token → clear setup instructions, no partial work.
- Profile violations → lint list per file, push refused.
- API failures → reported per file; state updated only for successes; safe to re-run.
- Changed on both sides → conflict flow above; git stays authoritative because Outline
  changes only land through a reviewed PR.
- Hub mode without a docs repo → verbs that need it suggest `/hub-add-repo` / `/hub-init`.

## Testing

- Unit tests for the pure functions: tree→document mapping, link rewriting (both
  directions), hash/state diffing, profile lint.
- `--dry-run` for manual verification of any real repo.
- End-to-end: run against a scratch collection on docs.wsagency.io; the marketplace repo
  itself is the guinea pig (its `docs/` published to an internal collection).

## Out of scope (candidates for v2)

- Product-level CHANGELOG / release-notes aggregation across sub-repos
- Interactive HTML explained page (`--html`)
- Fully automatic two-way sync with conflict auto-resolution
- Syncing `dev-docs/` anywhere

## Rollout

1. ws-project-hub v0.2.0 (schema + scaffolding + skill) — independent, ships first.
2. docs-agent v3.1.0 (routing + explain + publish/pull-back + script) — depends only on
   reading `project.yaml`.
3. Marketplace registry/README/reference updates per the repo's own docs convention.
