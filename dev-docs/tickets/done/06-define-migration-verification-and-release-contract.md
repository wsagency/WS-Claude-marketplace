## Question

What guarantees must existing configured repositories receive during the breaking migration, which observable scenarios and package checks prove the unified setup works end to end, and how should marketplace and `@wsagency/omp-ws` versions, changelog entries, references, and release sequencing communicate the cutover?

## Answer

The supported direct-upgrade window includes every known pre-5 marketplace configuration and adapter format present in repository history, not only the immediately preceding release. Migration uses versioned, sanitized fixtures derived from those released schemas. Unknown fields, unsupported custom trackers, ambiguous authored artifacts, and disagreements between sources stop before the write boundary and leave all inputs untouched.

For a repository with legacy state, plain `/ws-setup` performs discovery and presents a verified migration plan; there is no `update` verb. An existing valid `.wsagency/config.yaml` is canonical. Recognized missing values may be imported from `~/.claude/ws/config.yaml`, `.claude/ws-project.yaml`, `.claude/docs-config.yaml`, operational adapter files, and runtime-specific settings according to the dedicated mapping contract. Every recognized customized value is preserved. Repository-local legacy config files are removed only after the new config and dependent artifacts pass read-back and cross-file verification, and their removal is named in the single confirmed plan. User-global legacy configuration remains untouched because other repositories may still need it as migration input.

After the clean cutover, `/ws-status`, `/ws-commit`, `/ws-matt` flows, hooks, and runtime helpers do not read legacy configuration. When canonical core configuration is absent but a legacy source is detected, they fail closed before work, name the source, and direct the user to `/ws-setup`. They never continue with guessed Local or Jira defaults.

Intentional changes to an already valid setup use `/ws-setup reconfigure`. It first shows the current state and asks which domain to reopen—tracker/Jira, runtime policy, documentation, or all—so unrelated valid choices remain fixed. The detailed safety and tracker-transition contract belongs to its dedicated follow-up decision.

Release verification is layered:

1. Deterministic state, migration, and adapter tests cover new Local/no-Jira setup; every known legacy format; preserved customized values; aligned no-op rerun; conflict and unsupported-custom zero-write behavior; outside-git/origin gating; Jira-primary authentication failure; Local/Jira pending and field conflict behavior; hub-root and hub-sub-repository scope; documentation-worker partial failure and safe resume.
2. Versioned fixtures include real released outputs for ws-init-only, Local, Local/Jira, documentation-initialized, customized combined, and unsupported custom-tracker repositories. Inputs and expected outputs are checked in rather than generated by the code under test.
3. Claude Code installs the marketplace plugin from the release checkout and exercises `/ws-setup`. The actual `npm pack` tarball is installed into an isolated omp profile and exercises command and worker discovery, an existing-repository migration, an aligned no-op rerun, and absence of every removed setup surface.
4. Source and generated-artifact gates prove that `/ws-init`, `/ws-matt setup`, the legacy setup skill, stale references, and generated equivalents are absent.
5. Jira write behavior uses a deterministic fake adapter only; release verification performs no live Jira mutations. Read-only capability checks may validate the supported jira-cli interface, but they are not a substitute for the adapter contract tests.

This is a breaking marketplace release: `ws` advances from 4.4.0 to 5.0.0. The independently versioned 0.x native package advances from `@wsagency/omp-ws` 0.6.0 to 0.7.0, as required for any changed generated or native surface. The root changelog and its docs mirror identify the removed entries, the sole `/ws-setup` replacement, canonical config migration, the exact native package pairing, and the required existing-repository action.

One canonical user-facing migration guide documents package update, entering each repository, running `/ws-setup`, reviewing the migration plan, and verifying the subsequent no-op rerun. Changelog, release notes, command reference, package README, and installation guidance carry a concise breaking notice and link to that guide rather than duplicating it.

Release uses one reviewed commit containing implementation, generated output, references, changelog mirror, marketplace 5.0.0 metadata, and native 0.7.0 metadata. After it is merged, publish the already verified 0.7.0 tarball, verify registry metadata and a clean isolated installation, then tag that exact commit `v5.0.0` and publish the marketplace release. If npm publication or registry verification fails, do not create or announce the marketplace tag.
